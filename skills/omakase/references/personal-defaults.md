# Personal defaults and learning

Omakase is the user’s personal engineering workflow. Prefer a small, inspectable set of practices that improve their work over a comprehensive framework. Own investigations and disposable prototypes as well as production delivery. Use explicit scoping and workflow-specific evidence; long-running project orchestration remains outside the current contract.

## Default tool choices

Resolve tools by purpose using the project profile before using a global preference. For source, issue and PR context, prefer an available authenticated GitHub integration where the project uses GitHub. Use local repository evidence for code and documented entry points for execution. Follow project instructions for internal context and runtime observability; do not assume every project uses the same issue tracker or services. For rendered app evidence, use available browser or native-app control appropriate to the project.

These defaults are preferences, not prerequisites for every task. Project configuration can replace a default for one purpose while leaving the others intact. Discover actual callable capabilities; a configured name never makes a tool available or grants permission.

## Learn at the smallest durable scope

- **Explicit user correction:** distinguish a task instruction from a standing preference. If the user states it applies everywhere, update the relevant rule here or in the workflow reference. If it applies to one project, record it under `preferences` in that project’s ignored profile. If scope is unclear, honor it for the current task and propose where to keep it.
- **Operational discovery:** after a successfully verified, reproducible setup, validation, or tool-routing discovery, update the relevant project profile entry. Keep the established operational learning rules in project guidance.
- **Inferred preference:** present the proposed adjustment and supporting example; keep it provisional until the user confirms. Repetition is evidence to ask, not automatic authority to establish a new global rule.

Report persisted changes briefly: what changed, its scope, and why. Replace obsolete rules rather than appending contradictory reminders. Keep a concise reason with a durable rule when it prevents future misinterpretation; do not accumulate transcripts, per-task logs, or speculative lessons.

Honor read-only requests and repository authorization. If persistence would require an edit the task forbids, propose the change in the response instead. A global skill edit is repository work: isolate it, validate and independently review it, and publish only under existing authority. Do not silently commit or push a workflow change from an investigation. Never persist secrets, private task payloads, transient failures, or expanded external permissions.

## Check that learning helps

For substantive workflow changes, run representative scenario probes against the prior and revised guidance. Examine scope, routing, evidence, transitions and tool availability; record limitations honestly. Structural tests prove links and configuration shape, not agent compliance. Keep reusable scenarios in the manual catalog, and avoid claiming that a few simulated responses establish reliable performance across real projects.
